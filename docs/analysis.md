# PiTerm 项目缺陷分析与优化方案

本文档旨在分析当前 PiTerm 项目中存在的架构缺陷、性能瓶颈以及代码质量问题，并提出相应的优化建议。

## 1. 后端架构 (Rust/Tauri)

### 1.1 SSH 操作的阻塞风险（已完成）
**现状**：部分 SSH 命令（如 `write_ssh`, `resize_ssh`, `disconnect_ssh`）直接在 Tauri 命令线程中执行 `lock().unwrap()`。虽然 `ssh2` 库是同步的，但某些网络操作（如 `write_all`）在网络抖动时可能会产生不可预测的阻塞，进而导致前端 UI 卡顿。
**优化建议**：
- 将所有涉及 SSH 会话写入或可能阻塞的操作封装在 `tauri::async_runtime::spawn_blocking` 中执行。
- 引入超时机制，避免长时间阻塞。

### 1.2 监控采集效率低下（已完成）
**现状**：前端 `SingleSessionMonitor` 组件每 10 秒通过 `Promise.allSettled` 同时发起 5 个独立的 Tauri 命令（CPU, 内存, 磁盘, 网络, 操作系统）。每个命令都会在后端创建一个新的 SSH 通道并执行 shell 命令。
**缺陷**：
- **高并发负担**：短时间内在同一个 SSH 会话上开启过多通道可能导致服务端拒绝连接。
- **解析冗余**：多次执行 shell 命令增加了服务器负担和网络延迟。
**优化建议**：
- **统一采集接口**：在后端实现一个 `get_ssh_combined_info` 命令，一次性执行多个 shell 命令（通过 `&&` 或脚本）并统一返回 JSON。
- **差量更新**：仅在必要时请求操作系统等不常变化的信息。

### 1.3 会话管理与清理（已完成）
**现状**：SSH 会话存储在 `SshState` 的全局 HashMap 中。虽然提供了 `disconnect_ssh`，但如果网络异常断开或前端窗口崩溃，后端会话可能无法及时回收。
**优化建议**：
- **心跳机制**：利用 `ssh2` 的 keep-alive 功能定期检测会话存活状态。
- **自动清理**：实现一个后台任务，定期清理已断开或长时间无响应的会话。

### 1.4 错误处理规范化
**现状**：代码中大量使用 `.map_err(|e| e.to_string())`，导致错误信息类型丢失，前端难以根据错误类型进行差异化提示（如：认证失败 vs 网络超时）。
**优化建议**：
- 使用 `thiserror` 或 `anyhow` 定义自定义错误枚举。
- 规范化返回给前端的错误结构体。

## 2. 前端实现 (React/TypeScript)

### 2.1 冗余的数据获取逻辑
**现状**：`SingleSessionMonitor` 同时使用了事件监听 (`listen("monitor:sync-data")`) 和手动轮询 (`setInterval`)。
**缺陷**：如果后端已经通过事件广播数据，手动轮询会造成双倍的数据请求。
**优化建议**：
- 明确职责：优先使用事件广播机制（Push 模式），轮询仅作为兜底且时间间隔应更长。

### 2.2 性能优化
**现状**：监控面板涉及大量图表和实时更新的数值，缺乏细粒度的渲染控制。
**优化建议**：
- **组件记忆化**：使用 `React.memo` 包裹卡片组件，仅在数据真正变化时重新渲染。
- **Canvas/SVG 优化**：对于实时趋势图，考虑使用更高效的渲染库。

### 2.3 状态管理瓶颈
**现状**：`useTransferStore` 等 Zustand store 中存在 `// TODO: 这里是关键！需要对接实际的网络请求取消逻辑`。
**缺陷**：文件传输功能尚未完全闭环，缺乏取消和进度同步的后端对接。
**优化建议**：
- 完善后端文件传输的流式接口，支持 `AbortSignal` 式的取消操作。

## 3. 代码质量与工程化

### 3.1 关键逻辑缺乏单元测试
**现状**：监控数据的解析逻辑（如 `src-tauri\src\commands\monitor\network.rs` 中的字符串分割）非常依赖 Linux 命令输出格式。
**缺陷**：不同 Linux 发行版或工具版本的输出微差可能导致解析失败。
**优化建议**：
- 为所有数据解析函数编写单元测试，使用多种样本数据进行验证。

### 3.2 硬编码问题
**现状**：超时时间（10s）、采集间隔（10s）、SSH 加密算法配置等散落在各处。
**优化建议**：
- 提取到全局配置中心或环境变量中，支持用户自定义监控精度。

### 3.3 样式管理
**现状**：存在内联样式（如 `SingleSessionMonitor` 中的 `<style>` 标签）。
**优化建议**：
- 统一迁移至全局 CSS 或模块化 CSS 目录。
