# 配置文件重置与损坏问题分析报告

## 1. 问题描述
用户反馈应用配置文件（`settings.json`）经常出现被重置为默认值、数据丢失或内容损坏的情况。

## 2. 核心原因分析

### 2.1 多窗口并发写入冲突 (Race Condition)
这是导致文件损坏或内容清空的最主要原因。

*   **架构问题**：PiTerm 采用多窗口架构（主窗口、高级监控窗口、编辑器窗口）。每个窗口都有独立的 JavaScript 运行环境和 `useSettingsStore` 实例。
*   **并发写入**：所有窗口的 Store 实例都通过 `persist` 中间件指向同一个物理文件 `settings.json`。
*   **后果**：当多个窗口同时尝试调用 `writeTextFile` 修改配置时，由于缺乏跨进程/跨窗口的文件锁机制，极易导致写入冲突。例如，窗口 A 正在截断文件准备写入时，窗口 B 也开始写入，最终导致文件内容错乱或变成 0 字节。

### 2.2 状态同步引发的“写入风暴”
*   **循环同步**：`useSettingsStore` 在状态变更时会发出 `app:settings-change` 事件，而各窗口又在监听该事件并调用 `updateSettings` 更新本地状态。
*   **后果**：这种机制在多窗口环境下容易形成广播风暴，导致磁盘 I/O 极其频繁。写入操作越频繁，遇到并发冲突和文件损坏的概率就越高。

### 2.3 启动时的初始化竞态
*   **异步加载延迟**：Zustand 的 `persist` 中间件异步加载磁盘文件。在文件加载完成前的瞬间，Store 处于默认状态。
*   **错误覆盖**：`App.tsx` 中的 `initDeviceIdentity` 等初始化逻辑在组件挂载时立即运行。如果此时文件尚未加载完成，初始化逻辑会认为配置缺失（如 `deviceId` 为空），生成新数据并触发 `updateSettings`。
*   **后果**：这会导致一个“半初始状态”被保存到磁盘，直接覆盖了用户原有的完整配置文件。

### 2.4 健壮性缺失
*   **错误处理**：`createDiskStorage` 在解析 JSON 失败时，没有稳妥的回退机制。一旦文件因为写入中断导致格式非法，应用会直接回退到默认设置，并在下次保存时彻底抹除损坏但可能尚存数据的旧文件。

## 3. 技术链路总结

| 环节 | 实现组件 | 风险等级 | 备注 |
| :--- | :--- | :--- | :--- |
| **存储适配器** | `createDiskStorage` | 高 | 缺乏多进程原子化写入保护。 |
| **状态持久化** | `zustand/middleware/persist` | 中 | 异步 Hydrate 期间状态不确定。 |
| **应用初始化** | `App.tsx (useEffect)` | 高 | 抢跑在数据加载完成之前。 |
| **跨窗口同步** | `app:settings-change` 事件 | 中 | 导致冗余的磁盘写入操作。 |

## 4. 修改方案建议

### 4.1 方案 A：引入原子化写入与文件锁 (后端方案 - 推荐)
*   **实现**：取消前端直接读写文件的权限。在 Rust 后端实现一个带有 `Mutex` 保护的配置管理器。
*   **优点**：彻底解决并发竞争问题，确保数据一致性。
*   **操作**：前端通过 Tauri Command 获取/修改配置，后端负责原子化写入（先写临时文件再重命名）。
